## Work Breakdown

### Wave 1: Parser Upgrades (all 10 languages)

Each language's parser needs these changes:

| # | Change | Effort |
|---|--------|--------|
| 1.1 | Accept `"2.1"` version string (add to allowed versions) | Tiny |
| 1.2 | Add `element()` to typed pattern kinds | Small |
| 1.3 | Add `stringLength`, `upperCase`, `lowerCase`, `matches` to keyword/reserved set | Tiny |
| 1.4 | Verify `attributes` is in keyword/reserved set | Tiny |
| 1.5 | Add `FunctionRef` handling in function-call argument positions | Small |

**Verification:** `xform version "2.1"` parses without error. Parsing `match x: case element() => y;` produces valid AST.

### Wave 2: Evaluator — Missing Builtins (all 10 languages)

| # | Change | Spec § | Effort |
|---|--------|--------|--------|
| 2.1 | Implement `stringLength(s)` — codepoint count | 11.7 | Tiny |
| 2.2 | Implement `upperCase(s)` — locale-independent uppercase via Unicode | 11.7 | Small |
| 2.3 | Implement `lowerCase(s)` — locale-independent lowercase via Unicode | 11.7 | Small |
| 2.4 | Implement `matches(s, pattern)` — literal substring match (not regex) | 11.7 | Tiny |
| 2.5 | Fix `number()` to return `NaN` on parse failure (not raise XFDY0002) | 11.1 | Small |
| 2.6 | Fix `typeOf()` to return `"function"` for function references | 11.1 | Tiny |

| 2.8 | Verify `keys(map)` and `mapSize(map)` are wired up in builtin registry | 11.4 | Tiny |

**Verification:** Each function produces correct output against unit tests. `number("abc")` → NaN (not error).

## Implementation Order (per language)

Within each language, implement waves sequentially:

```
Wave 1 (parser) → Wave 2 (builtins) → Wave 3 (semantics)
    ↓
Wave 4 (Python only: test activation + expected.xml generation)
    ↓
Wave 5 (all languages: cross-validation)
```

**For Wave 4:** Only the Python implementer does this. The `expected.xml` files produced become the shared reference for Wave 5.

**For Waves 1-3:** Each language implementer works independently. Order is fixed within a language but languages can advance at different speeds.

## Risk Assessment

| Risk | Impact | Mitigation |
|------|--------|------------|
| JS/C/C++/Java/Kotlin implementations are incomplete or stubs | High — unknown current status | Survey these 5 implementations first before assigning work |
| `matches()` spec is literal string match but some impls may use regex | Medium — test behavior divergence | Pin down behavior: spec says literal. Add explicit test for regex chars `.*` treated literally |
| `number()` return-NaN change breaks existing XSLT comparison tests | Low — case01-16 don't trigger NaN paths | Audit existing fixtures for `number(x)` calls on potentially invalid strings |
| Swift monolith makes changes riskier | Medium | Consider breaking into files as part of Wave 1, or at minimum add regression test first |
| `XFDY0003`/`XFDY0006` error code rename breaks error fixtures | Low | Update error fixture expected codes alongside eval change |
